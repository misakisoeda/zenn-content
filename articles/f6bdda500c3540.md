## はじめに

転職して2か月目で、既存の画面を作り変える大きな機能改修を続けて担当しました。
いちばん大きいものは **24,008行・229ファイル** の PR になりました。レビューもかなり重くなり、リリース直前までずれ込みました。

PR は小さく出すべき、ということは知っていました。それでも 24,008行になりました。
振り返っても「どこで分ければよかったのか」を自分で説明できませんでした。振る舞いの変更と構造の変更が最初から絡み合っている仕事に見えて、機械的には分けられない気がしていたからです。

知っているのに、なぜできなかったのか。
自分で答えを見つけるべく『Tidy First? ―個人で実践する経験主義的ソフトウェア設計』（日本語版）を読みました。
本の要約はほかにも良い記事がたくさんあるので、ここでは書きません。この記事では、読んで引っかかったところを手がかりに自分の PR を読み返し、分かったことを書きます。

---

## 読んで引っかかった2つ

### 30章「コンスタンチンの等価性」で、あの PR を思い出した

30章には、ソフトウェアのコストはおおよそ変更のコストであり、変更のコストはおおよそ一握りの大きな変更のコストであり、それはおおよそ結合のコストに等しい、という話が出てきます。変更のコストはべき乗則に従って偏る、という説明です。

読んだとき、真っ先に頭に浮かんだのがあの 24,008行の PR でした。
自分の仕事のコストも、あの1本に偏っていたのではないか。それを確かめたくて、あとで自分の PR を測ることにしました。
後半の「おおよそ結合のコスト」という話は、読み返したあとで、自分の失敗を説明する鍵になりました。

### 18章・19章で、「次の最小の一歩」を見失っていたと気づいた

18章「バッチサイズ」と19章「リズム」は、整頓をどのくらいの単位とリズムで進めるかの話です。
19章には、振る舞いの変更の前に1時間を超えて整頓を続けているなら、必要な最小限の構造の変更を見失っている可能性が高い、という趣旨のことが書かれています。

本が言う「最小限」は、構造の変更のことです。
ただ自分に当てはめると、見失っていたのは振る舞いの変更のほうの最小の一歩でした。
**区切り（チケットで決まっていた範囲）は最初からあったのに、着手2日目に自分で外し、その後は次の最小の一歩が分からないまま書き続けていました。**

## 自分の PR も一握りに偏っていた

対象は、弊社プロダクトのフロントエンドで、2026年6月から9月中旬までに自分がマージした **19件** の PR です。

| 指標                                      | 値                                                   |
| ----------------------------------------- | ---------------------------------------------------- |
| PR の行数（追加＋削除）                   | 中央値 214行 / 最大 24,008行                         |
| 整頓だけの PR                             | 0件                                                  |
| 整頓と振る舞いの変更が混ざった PR         | 7件（整頓が先 0 / 整頓があと 1 / 交互 6）            |

※ 件名が refactor / style のコミットを「整頓」、feat / fix を「振る舞いの変更」とみなしました（本の「整頓」より広い分類です）。「交互」は、PR の中で両者が入れ替わりながら並んでいたものです。

行数を大きい順に並べると、偏りが出ました。

- 最大の1件だけで、19件の合計 37,630行の **64%**
  - コード本体に限っても約58%。この1件の設計ドキュメントとテスト（計約5,300行）を、分子と分母の両方から除いた値です（ほかの18件のテストは含んだまま）
- 上位4件で **87%**

上位4件は、すべて同じ画面まわりの変更でした。その画面を続けて担当していたので、集まること自体は当然とも言えます。
ただ、同じ画面の中でも、1本だけが突出しています。ほかの3件は平均約3,000行で、最大の1件の8分の1ほどです。

19件で「べき乗則だ」とまでは言えません。それでも、行数で見る限り、あの1本に偏っていました。
そこで、全件を浅く読むのではなく、この1件を深く読み返すことにしました。

## その1件を読み返した

### 完成形を一度に作ろうとした

タスクは、ある管理画面の一覧を作り変えるものでした。
チケットの範囲は、一覧と保存方式の変更まででした。
一覧の各項目に紐づく公開や外部連携まわりの設定（以下「追加の設定」）は、既存の編集画面をそのまま使う予定でした。

一方、最終的に目指すデザインでは、追加の設定まで一覧に組み込まれていました。
私はその完成形まで一度に作ろうとして、着手2日目から追加の設定にも手を付けました。
一覧と追加の設定はデータも画面もつながっていて、切り離せないように見えたからです。
区切りはチケットの時点で引かれていました。私はそれを自分の判断で外しました。

追加の設定は複数の主要ページにまたがっていて、PR の中でいちばん大きな塊になりました。

| コミットの塊     | コミット数 | コミット差分の合計（書き直しを含む） |
| ---------------- | ---------- | ------------------------------------ |
| 追加の設定まわり | 74件       | 16,858行                             |
| 保存方式の変更   | 21件       | 6,940行                              |
| 一覧まわり       | 28件       | 6,042行                              |

※ この PR のコミット259件（マージコミットを除く）のうち、件名に含まれる画面や機能の言葉で3つに振り分けられた123件の集計です。QA 用に切られた別チケットの番号が件名に付いた87件は、QA 対応として表から除き、後述で別に数えています。残り49件は件名から判別できませんでした。

書き直しを含むので、最終的なコードの量ではなく手数の比較です。

### QA の対応も、同じ PR に積んだ

私は、全部作り終えてからまとめてデザインの QA に出し、通ってからマージする進め方を取りました。
デザイナーの時間を何度も取ってもらうより、QA は1回にまとめたほうが早いと考えたからです。

QA は約1か月分の変更に対して1回で、その指摘への対応も、まだマージしていない同じ PR に積みました。

- QA 対応だけで 87コミット・8,577行
- そのうち半分以上（51件・4,838行）は、追加の設定まわりの修正
- 開いている間に、ベースブランチを4回取り込んだ
- QA 対応が、同じ PR の中のほかの変更とぶつかって、新しい不具合を生んだこともあった

QA 対応の半分以上は、範囲外の部分でした。

QA 対応まで含めると、当初は範囲外だった追加の設定には約21,700行（125件）、当初の範囲（一覧と保存方式）には約16,700行の手数がかかっていました。判別できなかった49件（約4,300行）をすべて当初の範囲に足しても、追加の設定はほぼ同等か、それ以上です。

当時は「この PR がマージされるまでは、続きもここに載せるしかない」と考えていました。
そう考えた時点で、一度に扱う変更のまとまり（18章の言う「バッチ」）は、QA が終わるまで膨らみ続けるしかなくなっていました。
実際には、QA 環境へはどのブランチでも載せられました。QA 対応はチケット自体が別だったので、せめてそれを別のブランチに重ねて、レビューの単位だけでも分ける道はありました。そうすれば少なくとも、QA 対応のレビューは本体と切り離して見てもらえました。

### 継ぎ足しで直し続けていた

259コミットの差分（追加＋削除、マージコミットは除く）を足すと **42,687行** になりました。最終的な PR の差分は 24,008行です。
差の約18,700行は、PR の中で書いては消した跡です。追加と削除の両方に数えているので、書いて捨てたコードにするとおよそ9,300行です。

象徴的だったのが、保存した後に画面の状態をサーバーの結果と合わせる仕組みです。
7/13 に入れてから、前提が崩れるたびにパッチを3回当て、途中で1回 revert をはさみ、7/30 に仕組みごと作り替えました。

20章「絡まりを解きほぐす」には、整頓と変更が絡まってしまったときの選択肢が3つ出てきます。そのまま進める、整頓と変更を別々のプルリクエストにする、**進行中の作業を破棄して初めからやり直し、先に整頓する**、です。
Beck は「どれも魅力的とは言えない」と前置きしたうえで、最後の選択肢を選んで実験するよう促しています。再実装するほど、新しい発見の可能性が高まるからです。
本の3択は整頓と振る舞いの絡まりの話ですが、振る舞いどうしが絡まった自分の場合にも、「捨ててやり直す」はありえたと思います。

私は絡まったまま継ぎ足し続けていました。同じ章に「サンクコストの誤謬がこの選択を難しくする」とあるとおり、書いて動いているコードを捨てる選択肢が浮かんだのは、パッチを重ねたあとでした。
最後に作り替えたときは、保存結果を画面の並び順に当て直す処理を丸ごと削れました。もっと早く捨てていれば、途中で当て続けたパッチは要らなかったはずです。

## 本を当てて見えたこと

### コミットは小さかった。大きかったのは振る舞いの変更の単位

コミットの大きさ（追加＋削除）は、整頓（refactor / style）のコミット62件の中央値が **62行**、振る舞いの変更（feat / fix）の中央値が **約64行**で、どちらも小さく刻めていました。整頓の62件のうち44件はあの1本なので、ほぼあの PR の傾向です。

一方で、整頓だけの PR は19件中0件でした。整頓と振る舞いの変更が混ざった7件のうち、整頓をすべて**先に**置いていたものも0件です。
多くは振る舞いの変更と交互に入っていて、件名を読むと、レビューの指摘を受けて整えたものが目立ちます。「次の変更を楽にするために先に整頓する」という使い方はしていませんでした。

そして、大きかったのは整頓ではなく**振る舞いの変更の単位**でした。
最初は「振る舞いの変更と構造の変更が絡み合っていて分けられない」と感じていました。ところが読み返すと、絡み合っていたのは構造と振る舞いではなく、**複数の振る舞いの変更どうし**でした。一覧の刷新と、保存方式の変更と、追加の設定の組み込み、そしてその QA 対応です。

前提を書かないまま作っていた期間は、日付に表れています。
区切りを外したのは着手2日目（6/30）で、前提を書き出した設計メモを PR に入れたのは約1か月後（7/29〜30）です。その間は、作りながら前提を詰めていました。

人の目が初めて入ったのは7/28で、保存後の状態を合わせる仕組みを作り替えたのは7/30です。因果とまでは言えませんが、人に見せて前提を書き出した直後に、パッチを重ねていた仕組みを作り替えられたことになります。

AI と一緒に書いたこともあり、コミットは細かく分かれていました。でも、コミットが細かいことと、変更の単位が小さいことは別でした。

### 見誤っていたのは結合だった、と今は考えている

30章に戻ると、変更のコストはおおよそ結合のコストだ、という話でした。

私が「切り離せない」と感じていたのは、一覧と追加の設定の結合です。
ただ、チケットの計画では追加の設定は既存の編集画面を使うことになっていて、一覧との結合は「その画面を開く入り口」だけに抑えられていました。
私は、完成形のデザインにある結合を、今の一歩にも必要な結合だと取り違えていました。そして、今の一歩には要らなかったその結合を自分で作り込んだ結果、変更のコストが1本に集まりました。

### 経験があっても区切りを外した理由

コミットを小さく刻むことは、できていました。
ただ、どこが切れ目かは、コードを書く技術ではなく、ドメインの理解から見えてくるものです。

転職して2か月目で、自分がそのドメインに不慣れなことは分かっていました。
それなのに、チケットに引かれていた区切りより、自分の「切り離せない」という見立てを優先していました。

前職でレビューをメインでする側にいたころの自分なら、着手2日目に「追加の設定も一覧に組み込みたい」と相談されたら、別のチケットに切り出すよう返していたと思います。
それでも、書く側に回って慣れないドメインに入ると、その目を自分に向けられませんでした。
不慣れなドメインでは、切れ目の見立てを一人で持たず、すでに引かれている区切りから始めるべきでした。

## 結論: 分ける単位は「QA を通してマージできる単位」だった

21章「先に整頓、あとに整頓、改めて整頓、整頓しない」は、整頓をいつやるかの章です。
本が扱っているのは整頓ですが、読みながら、同じ問いは振る舞いの変更にも立てられると思いました。この機能は今やるのか、あとでやるのか。

自分の場合の答えは、**追加の設定は、あとでよかった**です。
しかもその答えは、着手の時点でチケットに書かれていました。問題は区切りを見つけられなかったことではなく、範囲を広げるときに、その区切りを問い直さなかったことです。

チケットの範囲こそが、QA を通してマージできる単位でした。チケットの計画自体がそうなっていたので、一覧と保存方式の変更だけで、一度 QA を通せたはずです。
新しい一覧からは、追加の設定だけ既存の画面を開く形で残しておけばよく、橋渡しはその入り口をつなぐ分だけです。
切り離せないように見えたのは、思い込みだった、と今は考えています。

もちろん、範囲内だけでも、QA 対応を除いた手数で見て約1万3,000行あり、小さな PR ではありません。
それでも、その範囲で一度 QA を通してマージし、追加の設定を次の PR にしていれば、増える手間は主に入り口の橋渡しと、QA もう1回分だったと見ています。

実際の QA 対応は、追加の設定以外の分が3,739行（36件）、追加の設定の分が4,838行（51件）でした。
分けていれば、ほかの変更とぶつかって生まれた不具合の分は減った可能性があります。ただ、ここでは控えめに、総量は変わらないと仮定します。それでも変わるのは、1回あたりの量と、直す場所です。分けていれば、1回目の QA 対応は3,739行の規模で済み、しかもマージ済みの土台の上で、未マージのほかの変更とぶつからずに直せます。
1か月分の変更を1回の QA にかけ、8,577行の対応をマージ前の同じ PR に積むよりは、軽かったはずです。

コードをどれだけ小さく整頓しても、振る舞いの変更の単位が大きいままではバッチは小さくなりません。
次の最小の一歩は、範囲を決める段階で一度見つけておき、範囲を広げたくなるたびに、そこへ戻って問い直すものでした。

## 測定の限界

最後に、今回の測り方の限界を書いておきます。

- **squash merge のリポジトリでは測れません。** PR の中のコミットの並びを見ているためです。
- **コミットの件名（prefix）に頼った分類です。** 実際に読むと、件名と中身が違うコミットがありました。
  - 「refactor」と付けたコミットで、保存に失敗したときの画面の流れまで変わっていた
  - 「fix」と付けたコミットに、直していない別の処理へのコメント追加が混ざっていた
- **コミットの前後関係は、因果関係ではありません。** 整頓のコミットが先にあっても、それが「後の変更を楽にするために整頓した」とは限りません。機械的な分類は読む順の当たりを付ける道具にとどめ、本体は目で読みました。
- **行数はコストの代わりの指標にすぎません。** かかった時間やレビューの負担は、行数だけでは測れません。
- **結合は測っていません。** 「見誤っていたのは結合だった」は、読み返しからの解釈です。
- **19件では、べき乗則とまでは言えません。** 偏りがある、というところまでです。

## おわりに

『Tidy First?』を片手に自分の PR を読み返すと、整頓のコミットは小さかった一方で、振る舞いの変更と分けて先に出すことはできていませんでした。
そして何より効いていたのは、整頓ではなく振る舞いの変更の区切りでした。
本は整頓の本ですが、バッチサイズ、リズム、絡まりの解きほぐし方、結合という道具は、振る舞いの変更の区切りにも、読み替えれば当てられました。
知っていることとできることの間には、範囲の区切り方や QA の進め方といった、コードの外の判断がありました。

次からは、この3つを判断の目安にします。

- チケットの範囲外の画面に触れるコミットを作ったら、その日のうちに区切りを出し直して相談する
- 書き始める前に前提をメモに書き出し、一度人に見せる
- 同じ仕組みへの修正が3回目に入ったら、継ぎ足す前に捨ててやり直すことを検討する
